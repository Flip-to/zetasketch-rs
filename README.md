# zetasketch-rs

> Unofficial: not affiliated with or endorsed by Google. Different from the `zetasketch-rs` crate
> (a separate port by another author).

A byte-compatible Rust port of [Google ZetaSketch](https://github.com/google/zetasketch)
HyperLogLog++, the sketch format that BigQuery `HLL_COUNT.*` produces and consumes.

- Decodes `AggregatorStateProto` sketches, both sparse and dense.
- Merges them the way the reference does: max over **decoded** registers, never a bytewise max
  over serialized bytes. Sparse sketches are promoted to dense, and precision is lowered when
  the operands differ.
- `estimate()` returns what `HLL_COUNT.EXTRACT` / `HLL_COUNT.MERGE` return. It includes the
  bias-correction tables and the switch to linear counting at low cardinalities.
- `serialize()` returns what `HLL_COUNT.MERGE_PARTIAL` returns, byte for byte.
- `add_long` / `add_int` / `add_str` / `add_bytes` hash values with `Fingerprint2011`, the same
  hash as the reference and BigQuery.
- `Accumulator` folds many serialized sketches without per-sketch allocation, with the same
  result.
- No dependencies and `#![forbid(unsafe_code)]`.

To fold many stored sketches (one result per group, thousands of inputs), use `Accumulator`.
It gives the same bytes and estimate as the reference fold, parses without copying, and
allocates nothing per input in steady state:

```rust
use zetasketch::Accumulator;

let mut acc = Accumulator::new();
for group in groups {
    acc.reset();                              // keeps its buffers
    for sketch in group { acc.add_bytes(sketch)?; }
    emit(acc.estimate());
}
```

`cargo bench --bench fold` (2,000 synthetic sketches per workload; one Windows machine,
2026-10-29), in microseconds per sketch:

| Workload | Reference fold | `Accumulator` |
|---|---|---|
| Mixed: p = 15, 70% sparse inputs | 19.9 | 8.7 (2.3x) |
| Mixed precision: 1 in 20 at p = 12 | 50.0 | 16.5 (3.0x) |
| Sparse-heavy: 1 to 12 values each | 60.1 | 1.7 (34.6x) |

Results are identical in every case. Where the time goes, and an optimization that was tried
and rejected, is in `docs/findings/20261029_fold_cost_breakdown.md`.

```rust
use zetasketch::HyperLogLogPlusPlus;

// Bytes from BigQuery: SELECT HLL_COUNT.INIT(user_id) ...
let mut acc = HyperLogLogPlusPlus::from_bytes(&sketch_a)?;
acc.merge_bytes(&sketch_b)?;                 // HLL_COUNT.MERGE_PARTIAL semantics
let distinct = acc.estimate();               // == HLL_COUNT.EXTRACT
let bytes = acc.serialize();                 // == HLL_COUNT.MERGE_PARTIAL bytes
```

## Development

```bash
cargo test --release
cargo clippy --all-targets -- -D warnings
uv run scripts/check_docs_layout.py
```

The other scripts regenerate the generated inputs:

- `scripts/gen_bias_data.py <Data.java>` rebuilds `src/bias_data.rs` from the reference tables.
- `scripts/gen_bigquery_fixtures.py --project <p>` re-queries BigQuery for the fixtures.

## Differences from Java ZetaSketch

Where Java throws or corrupts state, this crate does not. Everywhere else the output matches
byte for byte. Details are in
[`docs/specs/20261028_hllpp_port_with_bigquery_parity.md`](docs/specs/20261028_hllpp_port_with_bigquery_parity.md).
The notable one: Java mishandles a sketch folded through a lower, then higher, then lower
precision. This crate matches BigQuery there.
